# VaultNap

A place to keep track of games that three friends might play together on **Windows 11 gaming PCs**. We mostly use Steam, but other PC storefronts are fine when a game isn't available there.

## Game shortlist

**[Browse the game list →](games/README.md)**

| Section | Meaning |
| :--- | :--- |
| [Possible Games](games/README.md#possible-games) | Games we consider ready to play together |
| [Early Access](games/README.md#early-access) | Games in Early Access that might benefit from more development before we play |
| [Coming Soon](games/README.md#coming-soon) | Games not yet released, including into Early Access |

The shortlist is a set of **candidates**, not a verified list of games supporting three-player co-op. Platform support, player counts, release status, and store review numbers may need checking before we choose a game.

## How updates work

The owner makes all repository commits manually. Proposed updates are discussed in chat and delivered as a **ZIP archive of changed repository files**, plus a suggested **commit message**. Extract the ZIP at the repository root, inspect the changes, and commit them yourself. The assistant may **read** the repository but must never write to GitHub.

10. **Review refreshes always include sorting.** Whenever Steam reviews are refreshed in either `Possible Games` or `Early Access`, always re-sort the refreshed section by **Percent descending**, then by the **exact (unrounded) Steam review count descending** for percentage ties, even if the user asks only to update reviews. If refreshing both sections, sort each one independently. Do not re-sort sections whose review data was not refreshed. `Count` is displayed as the exact integer below 1,000 or as `k` with one decimal place and conventional half-up rounding for totals of 1,000 or more (e.g. 1,250 → `1.3k`). Use exact source counts, never abbreviated numbers, for tie-breaking. Preserve names, descriptions, Steam links, dates, section assignments and all unrelated content unless separately requested.
11. **Early Access timeline checks.** `Start` is the actual Steam Early Access launch date, not the 1.0 release date. `Est. End` is the available full-release date or developer-provided release target; if a developer provides only an Early Access duration, a broad calendar forecast may be derived from the verified start date. In `games/README.md`, keep `Est. End` concise: show the stated date/period without `(est.)` or `(planned)`; for a range show **only its latest/upper-end date or period** (e.g. `2028–2029` → `2029`, `Late 2027–Late 2028` → `Late 2028`). `n/a` means no usable current timing. Do **not** present an expired forecast, a minimum duration, or an invented precise date as a target. Always document sources, whether a date is confirmed/explicit/derived, limitations and uncertain windows in `docs/PROJECT_CONTEXT.md` so the compact catalog does not imply certainty. A dates-only change does not trigger review-data sorting.
12. **Release status and section transfers.** When asked to check Early Access membership, verify current Steam status and move any title that has reached full 1.0 or launched outside Early Access into `Possible Games`, retaining its original link, description and latest existing review figures unless specifically asked to refresh them. Remove the title from Early Access (no duplicates) and place it in Possible Games using the approved descending Percent/Count ranking. Record exact move reasons and 1.0 release dates in project context. Do not move still-Early-Access games simply because they are playable. Preserve other sections and catalog fields.
13. **Coming Soon release timeline and sorting.** `When` is the developer/publisher's latest announced date or period for the game's **first public release** (including an Early Access launch, if that's how it will first become available), not a playtest/beta date. Check the current developer/publisher announcement and Steam store page; prefer the official developer-stated date over a region-specific store date, and document differences. Keep the catalog concise without `(est.)` or `(planned)`; for a stated date range use only its **last/upper-end** date or period (e.g. `Q2–Q3 2027` → `Q3 2027`). Use `n/a` when no current usable release target is available. **Always sort Coming Soon by the calendar timing descending (latest dates first); put `n/a` last, keeping original relative order within unknowns and exact ties.** Treat year- and quarter-only dates as ending on their last possible calendar day for sorting, not as asserted exact release dates. On each release-date update, reapply this sorting. **Early Access prefix:** If the developer/publisher confirms that the game’s first public release will be in Early Access, put `EA ` before the announced date/period in `When` (e.g. `EA Feb 8, 2027`, `EA Late 2027`). Apply the prefix to confirmed Early Access *release plans*, not betas, demos, playtests, campaign/edition preorder early unlocks, or similar limited-access offers before a full release. Do not infer Early Access merely from a future date. If the EA release is known but no timing is available, display `n/a` without a prefix; keep full-release first launches unprefixed. **Sort by the calendar period/date ignoring the `EA` prefix**; put unknowns last. Record original source, distinctions between confirmed dates/targets and uncertain schedules, and the check date in `docs/PROJECT_CONTEXT.md`. Do not refresh reviews, add or remove games, or move games between sections unless separately requested.
